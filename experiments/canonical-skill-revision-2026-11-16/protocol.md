# Canonical skill implementation and development rerun

16 November 2026. The author authorized Astra to edit the canonical skills to implement the four adjudicated rules, depth selection and code checks, then rerun tests. This supersedes the earlier experiment's boundary against changing canonical skills. It does not authorize global installation, a release or publication.

## Preservation and ownership

The exact pre-revision skills, scripts, tests, plugin manifest and selected documents are in `baseline/`, with `baseline-manifest.json`. Pre-existing README changes are included. Historical experiments, corpus bytes, accepted foundations, original labels and debate records remain unchanged. The prior debate's old canonical-file hashes describe its historical comparison inputs, not an invariant requiring the newly authorized revision to be undone.

Astra owns the canonical skill folders and implementation notes. The parent owns package documentation, metadata, test orchestration and the report. An independent reviewer examines the actual source diff. Fresh Terra contexts execute development tasks without reading the adjudication rationale or previous outputs. No staging, commit, release, service registration or global install is part of this task.

## Verification

1. Run the existing Python software tests on the frozen baseline and revised source. Keep the command, exit status, count and full log. Existing tests cover executable behavior; passing them cannot validate new prose instructions.
2. Validate both completed skills with the skill-creator validator. Check their links, conditional resources, independent use and paired author-reference copies. Test the annotation prototype's existing mechanical contract separately.
3. Apply each arm to the same twelve raw tasks: ten known synthetic development tasks and two new parent-authored drafting tasks. Two fresh contexts per arm each receive one six-task group. They may read their assigned skill folder and relevant references, supplied notes/constraints and the common original function catalogue. They cannot read another arm, old examples, expected results or adjudication reasoning.
4. Preserve actual outputs and their input/skill hashes. Re-run declared mechanical contracts against the pure delivered bodies, with the original draft as the growth baseline when relevant. Review findings against supplied evidence instead of treating every number change as an error.
5. Give a fresh reviewer masked output pairs, the task, supplied facts and user-facing notes. Inspect scope, fidelity and usefulness separately; allow ties and uncertain effects. Keep arm identities outside that review packet. Source auditing and model preferences do not establish human approval.

## Limits

These are matched development tasks with one output per arm per case, clustered in six-task contexts. Ten cases are already known to the project; the two drafting cases are synthetic, not a human-authored holdout corpus. Different model executions add variation. A preference cannot be attributed solely to an individual rule, and no statistical superiority, optimized writing quality or learning transfer follows. The paragraph-coder agreement study is a separate experiment; this rerun does not reclassify its source paragraphs or replace its reported results.

No new semantic linter, calibrated form profile, grammar engine dependency or automatic delivery hook is implied by a skill instruction. Enforced byte-level contracts and editorial/source judgments remain distinct.
